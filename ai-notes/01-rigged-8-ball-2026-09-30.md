# 01 · magic-8-ball — a Magic 8-Ball you can rig by link

## The idea (2026-09-30, Rob)

> You go onto Magic 8-Ball forward slash set, and you can set whatever the next answer will be that it
> gives. So then it gives you a link. There's no back end or anything. The answer that you want it to
> give is encoded in the URI, in like a cipher or something so it's not just plain readable. So then you
> can send someone a link to be like, well, we could ask the Magic 8-Ball, what did it say? And then they
> click and it goes through and it's like blah, blah, blah… and then bang, it comes up with the thing
> that the first person wrote and sent with the link.

Live: https://rt567.github.io/magic-8-ball/ (the ball) and https://rt567.github.io/magic-8-ball/set/
(the rigging page). Repo github.com/RT567/magic-8-ball, branch `main`, legacy GitHub Pages from `/`.
Built in one session on 2026-09-30 by a Claude sub-agent working for an orchestrator that was building
several of Rob's silly sites at once.

## How it works

- **`/set/`**: type the answer (max 80 characters, counted as graphemes so 👨‍👩‍👧 is one), see it
  live on a mini 8-ball, get a link with **Copy link**, **Share…** (`navigator.share`, where the
  browser has it) and **Try it** (opens the link in a new tab). The main page never links to `/set/`,
  and `/set/` is `noindex`.
- **`/`**: the ball. With a valid payload in the fragment, *every* shake gives the rigged answer
  (consistent is funnier and more convincing). With no payload or a garbage one it gives one of the 20
  classic Magic 8-Ball answers at random, so a rigged link behaves exactly like a normal 8-ball link.
  The answer is read from `location.hash` on each shake.

## Link encoding (`codec.js`): obfuscation, not security

The payload lives in the **URL fragment**: `https://rt567.github.io/magic-8-ball/#<payload>`.
Fragments are never sent to a server, and the link looks like a normal 8-ball link.

```
bytes = [salt] [0x8b ^ k0] [utf8(answer)[i] ^ k(i+1) ...] [checksum ^ k(n+1)]
k(i)  = KEY[i % len] ^ ((salt + 167*i) & 255) ^ ((13*i*i + 91) & 255)
payload = base64url(bytes), no padding
```

- `KEY` is a fixed string in `codec.js`; `salt` is one random byte per link (the set page keeps one
  salt per visit so the link doesn't flicker while typing). The same answer gives a different link each
  time, and repeated letters don't show as repeated bytes.
- The version byte (`0x8b`) + a 1-byte rolling checksum + strict UTF-8 decoding reject garbage, so a
  mangled link falls back to random answers instead of showing junk. 200k random base64url strings
  produced 0 false decodes.
- **Anyone who reads `codec.js` can decode a link.** It only stops the recipient reading the answer
  in the URL at a glance. The set page says so ("scrambled in the link, not secret").
- Round-trips emoji, ZWJ sequences, accents and CJK. Changing `KEY`, `VERSION` or `k()` breaks every
  link already sent: if the format ever has to change, bump `VERSION` and keep decoding the old one.

## Design

- **Rob's direction (2026-09-30, mid-build): no question input, and "just the ball".** The first
  draft had a title ("Magic 8-Ball", tagline "Ask · Shake · Obey"), an "Ask it a yes-or-no question…"
  text box, a caption line under the ball and an iOS "enable shake" button. Rob asked for all of that
  to go: the main page is now only the ball centred on a plain background plus a tiny, faint
  "tap to shake" / "click to shake" hint. The set page was trimmed to match (mini ball preview, answer
  box, link + buttons, one line of fine print; no title, tagline or suggestion chips). There's a
  visually-hidden `<h1>` for screen readers.
- **Rob, same day: must be good on desktop too.** Ball size is `--d: min(84vw, 62svh, 560px)`, so it's
  ~476px at 1366×768 and 560px at 1920×1080, dead centre (the hint is absolutely positioned under it so
  it doesn't pull the ball off-centre). On mouse devices the hint says "click", the cursor is a pointer,
  and the ball lifts slightly on hover (shadow shrinks). Keyboard: Space/Enter anywhere on the page
  shakes (the ball is a real `<button>`, so Tab + Enter/Space works too) with a brass focus ring.
- Palette: plain oxblood background (`#2a1217`), glossy black ball built from CSS radial gradients, a
  warm bounce light on the lower right, a fixed specular highlight; the icosahedron face (inline SVG in
  `die.js`) is the only blue on the page. Fonts: Fraunces (the "8", the whispers) and Barlow
  Condensed (the answer text, the hint) from Google Fonts.
- **The sequence** (`app.js`, ~5.5s first time, ~4.5s after): the ball shakes (whole ball translates,
  only the body rotates so the highlight stays put, like a real light source) → first time only, the
  "8" disc rolls up over the top of the sphere (translate + scaleY foreshortening) and the window rolls
  in from the bottom → the window goes murky (blurred swirling blobs + rising bubbles) while teasers
  murmur *inside the window* ("The spirits are consulting…", "Blah blah blah…", "Hmm. Hmmmmm." …, then
  "Something is surfacing…") and a blurred triangle lurks in the murk → **bang**: the die snaps up with
  an overshoot, a blue flash in the window, a bump of the ball, `navigator.vibrate` on Android. Then
  the die bobs gently and the hint says "tap to ask again". Re-shaking sinks the die first.
- **Text on the triangle** (`EightDie.fit`): the text block flows between two floats with
  `shape-outside` polygons, so lines are naturally triangle-shaped (narrow near the apex). The fit
  loop measures an off-screen clone (so animation transforms don't skew numbers) and picks the largest
  font size that keeps every line inside the triangle, then nudges the block toward the triangle's
  visual centre. Pathological no-space strings fall back to `word-break: break-all`. Text is
  uppercased by CSS, like the real thing; the set page preview shows exactly what will appear.
- **Phone shake**: `devicemotion` is used where it needs no permission (Android etc.; 3 big jolts
  within 800ms). iOS gates motion behind a permission dialog, and a dialog popping up during the
  suspense (or an extra button on the page) wasn't worth it, so iOS is tap-only.
- Link previews: `og:title` "Magic 8-Ball", innocent description, `og.png` is a 1200×630 screenshot of
  the idle ball (no spoilers; the preview can't know the answer anyway since it's in the fragment).
  `apple-touch-icon.png` is a render of `favicon.svg`.
- `prefers-reduced-motion`: shake is near-instant, murk/bob animations off, waits capped at 350ms.

Push to `main`; legacy Pages builds from `/` in a minute or two
(`gh api repos/RT567/magic-8-ball/pages/builds/latest --jq .status`). Local: `python3 -m http.server
8764 --directory .`.

## Gotchas

- Changing the hash on the same page doesn't reload it; `answer()` reads `location.hash` at shake time
  so that's fine, but when testing a fresh open, actually reload.
- Chrome DevTools screenshots of a background tab can catch transitions frozen mid-way (looked like a
  blurry die once); take another screenshot before believing it's a bug.
- Beads (`bd`) is initialised in this repo; `.beads/` is committed.
